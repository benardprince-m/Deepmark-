# DeepMark repository audit synthesis and cleanup report

**Repository:** `/home/ubuntu/deepmark-review/Deepmark-`  
**Synthesis date:** 2026-10-04  
**Scope:** Consolidated frontend, API, routing, Supabase, configuration, and documentation audit results supplied for this task. This is a read-only source review; it does not establish what is currently deployed or prove live database/provider behavior.

## Executive summary

The audits converge on a small number of release-critical themes: **authorization and tenant boundaries need immediate verification and correction; auth bearer tokens are logged; AI usage controls are stubs rather than enforcement; billing/subscription writes can fail or affect the wrong workspace; and many dashboard actions/data states are presented as live despite being inert or fabricated.** The repository also has a confirmed lint gate failure and substantially stale operational documentation.

This report normalizes source audit labels to **P0** (contain before a production release if the path is deployed/reachable), **P1** (high-priority correctness, availability, or release readiness), and **P2** (lower-risk quality, verification, or cleanup). Where a finding depends on deployed grants, environment, or external consumers, that dependency is called out; no live Supabase, Stripe, mail provider, or hosting checks were performed.

### Priority definitions

- **P0 — security/financial boundary:** direct authorization, cross-tenant, credential exposure, or equivalent risk. Verify production exposure and contain first.
- **P1 — major product or release risk:** broken auth/billing paths, incorrect authoritative data, nonfunctional primary actions, or CI/deploy blockers.
- **P2 — maintainability, accuracy, or low-risk follow-up:** documentation, visual/accessibility, dormant code, and owner-verification work.

## Ordered cleanup plan

1. **P0 — Contain and prove security boundaries.** Stop logging raw reset/verification bearer tokens; assess/redact existing log exposure and invalidate affected outstanding tokens where warranted. Enforce verified-account and account/workspace ownership checks centrally. Remove caller control over Stripe customer IDs. Validate velocity content ownership before any service-role write. Inspect the deployed Supabase grants/policies and RPC EXECUTE privileges, especially log/usage inserts and `increment_usage`; add a forward corrective migration if exposure exists. Do not infer production status from migration files alone.
2. **P1 — Restore reliable auth, billing, and quota behavior.** Allow only intended anonymous recovery/verification endpoints by exact path while retaining token validation/rate limits. Deliver reset/verification links through a mail provider instead of logs and provide the browser pages those links target. Correct Stripe webhook persistence/error handling and workspace scoping; configure real Price IDs/secrets. Replace allow-all/process-local AI quota logic with bounded inputs, durable atomic per-tenant metering, and server-side gates before provider calls.
3. **P1 — Stop presenting placeholders as real customer data/actions.** Wire or clearly disable pricing, settings, chat, planner, dashboard, and plan actions/content. Separate analytics errors from valid zero data; mark derived estimates/demo values and threshold-calculated variants accurately. Implement missing billing return pages or point URLs at existing pages.
4. **P1 — Clear release gates and reconcile schemas.** Resolve the reported 44 ESLint errors, then run lint, TypeScript, and production build in a clean checkout. Fix incorrect schema joins/upsert conflict targets and inspect Supabase query errors rather than silently returning zero/success. Keep build failure for `/api/v1/ai/provider` tracked separately until its cause is reproduced and localized.
5. **P2 — Reconcile route tree, documentation, and environment contract.** Remove the obsolete manual-migration instructions immediately; refresh route/API inventories from actual `route.ts` files and methods; date or archive old audits/ADRs/release claims. Document `OPENROUTER_API_KEY`, the app URL, and the lack of email delivery accurately. Verify privacy/terms statements with their owners.
6. **P2 — Prune only after a reference/ownership check.** Remove locally orphaned files/dependencies only after checking package/script usage and external consumers. Preserve schema scaffolds, migration history, valid configs, and linked diagrams; use new migrations rather than editing historical SQL.
